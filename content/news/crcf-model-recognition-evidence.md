A carbon estimate can look precise long before the evidence supporting its use is clear. The number may be reproducible in software yet unsuitable for the particular land system, input data or claim being considered. For agroforestry teams, the useful question is not simply whether a model produces an output. It is whether that output can be used for the intended purpose under stated conditions.

## Keep recognition and project verification distinct

The European Commission's certification-methodology page links a recognition protocol and application template for models and proxy-based frameworks, labelled as draft versions. The linked documents are dated September 2026. The template distinguishes assessment of a tool, its application domain, input specification and uncertainty treatment from verification of future project inputs. It does not treat recognition as approval of every later project using the tool.

The protocol's assessment structure includes transparency, scientific credibility, suitability and accuracy for models, with representativity and reliability addressed for proxy frameworks. These are features of the published recognition material, not evidence that FarmTree has received recognition. This article makes no such claim. Its practical recommendations concern how a project team can prepare reviewable model evidence without overstating its regulatory status.

## Ask what, exactly, is being assessed

“The model” can mean an equation, a software release, a collection of linked components or an entire service. Those are different objects. Begin an internal evidence review by recording the precise version used, the material dependencies and the transformations applied before and after calculation.

For example, a model may receive weather data through a preprocessing routine maintained separately from the calculation engine. Updating that routine can change the inputs even if the visible product version remains the same. A reproducibility record should therefore cover the working chain rather than only the name displayed on the screen.

Do not treat this inventory as a demand to publish confidential code or personal farm data. Identify what evidence a reviewer needs, who is authorised to access it and how access can be provided appropriately. A claim that information is sensitive does not, by itself, explain how a conclusion can be independently assessed.

## Describe the conditions of use before quoting the result

A useful model may be well supported for some conditions and weakly supported for others. Record the land systems, management changes, input ranges and locations represented by the evidence available to the team. Where an intended use goes beyond that evidence, label the extrapolation explicitly.

An agroforestry scenario with a different tree–crop arrangement is not automatically covered merely because the model has been used for agriculture. Ask which part of the supporting evidence addresses that arrangement, which part is an assumption and what independent observations could challenge it. This is a technical review question, not a reason to reject all modelling when evidence is incomplete.

The decision may be to narrow the intended use, collect additional observations or present a result as exploratory. Those are different outcomes and should be recorded distinctly. A limitation acknowledged before a decision is more useful than a qualification added only after a result is challenged.

## Separate calibration from a test of performance

In an internal review, trace which observations were used to set or adjust the model and which were reserved to examine its performance. A good fit to information used during development does not answer every question about use elsewhere. Ask the technical team to explain the independence and relevance of the evaluation evidence in terms a project reviewer can follow.

Keep the individual evidence records accessible. A headline performance statistic may hide variation between conditions, periods or management regimes. Where the available evaluation is uneven, avoid presenting an overall result as if each proposed use were equally supported.

The Commission template gives calibration, validation and uncertainty their own dossier sections. A practical response is to maintain a small evidence index linking each important claim to its supporting record, including any limitation. The index should help a reviewer locate evidence, not replace the evidence with a checklist of reassuring labels.

## Make uncertainty operational

An uncertainty note is most useful when it changes how a result is used. Identify which uncertainty comes from observations, which comes from assumptions and which concerns how the model represents the system. Then ask which of those uncertainties could alter the decision being considered.

For a planning exercise, teams can compare plausible alternative inputs and management assumptions. Record the purpose of each comparison rather than calling every range a confidence interval. A sensitivity scenario is not automatically a statistical estimate of uncertainty, and neither should be described as a guarantee.

If an output is intended for a formal carbon claim, the relevant methodological treatment must be followed separately. A scenario comparison on the [FarmTree Platform](/platform/) does not itself establish that treatment. The related [CRCF project-design article](/crcf-mineral-soils-project-design/) addresses the records and responsibilities needed around the activity as a whole.

## Review changes before replacing an established result

Maintain a change record when data, software or assumptions are updated. State whether the change corrects an error, extends the evidence base or changes the intended application. Rerun a proportionate set of representative cases and investigate material differences before substituting new outputs into an existing decision document.

The practical takeaway is to request a model-use statement alongside the result: version, purpose, input provenance, evidence coverage, uncertainty and limitations. That statement will not confer recognition, but it makes an unsupported leap from calculation to claim easier to detect and a legitimate technical assessment easier to conduct.
